# 設計判断の記録

実装中に行った設計判断を、理由と検討した代替案とあわせて記録します。
実装前の計画は [plan.md](plan.md)、提出物としての概要は [README](../README.md) を参照してください。

各項目の形式: **決定** / **理由** / **検討した代替案**(ある場合)

---

## 1. 構成・技術選定

### 1-1. ディレクトリ構成とコードの置き場所

- **決定:** 機能単位の構成(feature-based)。ポートフォリオ機能のコードは `src/features/portfolio/` に集約し、置き場所は「使う場所の近くに置く」を基本にする。
  - 1つのコンポーネントだけが使う部品(スケルトン、アイコン)は同じファイルに置く
  - 状態や副作用を持つロジックはカスタムフックに切り出す
  - 機能固有の純粋な処理は `features/portfolio/utils/` に置き、単体でテストする
  - 複数の機能で使える汎用的なものだけを `src/components/`・`src/hooks/`・`src/utils/` に置く
- **理由:** 機能の追加・削除がフォルダ単位で完結し、汎用フォルダに機能固有の知識が漏れない。
- **代替案:** 画面固有の DOM 操作(キーボードフォーカスの追従)を `src/utils/` に置く案は、チャートが `<g>`・一覧が `<button>` という画面固有の構造に依存するため見送った。ルーティングは1画面のため `app/page.tsx` のみとし、参考記事にある `projects/[projectId]` のような構成は採用していない。

### 1-2. パイチャートは自前の SVG で実装

- **決定:** グラフライブラリを使わず、SVG と角度計算(`donut-geometry.ts`)で実装する。
- **理由:** 「12時起点・降順・時計回り」「要素間の隙間」「フォーカス時の半透過と強調」「各要素をボタンとして扱うキーボード操作」「当たり判定の固定(2-4)」をすべて意図どおりに制御できる。形状計算は純粋関数として単体テストでき、バンドルも小さい。
- **代替案:** Recharts。`startAngle`・`paddingAngle`・`activeShape` で大半は実現できるが、半透過やアクセシビリティ、当たり判定の制御はライブラリの描画・イベント処理を回避する必要がある。複数種類のグラフがあるプロダクトなら、一貫性のためライブラリを選ぶ。

### 1-3. データ取得とレスポンス検証

- **決定:** Route Handler(`GET /api/portfolio`)がモック JSON を返し、画面はクライアント側で取得する(SPA)。レスポンスは Zod で検証し、アプリ内では camelCase の型に変換して扱う。
- **理由:** 実 API に差し替えても取得側のコードが変わらない。API の形が変わっても影響は `schemas.ts` に閉じ、想定外のデータはエラー表示につながる。

### 1-4. Tailwind CSS は PostCSS 経由で読み込む

- **決定:** create-next-app のテンプレートが使う `@tailwindcss/turbopack` ローダーではなく、`@tailwindcss/postcss` を使う。
- **理由:** 別プロジェクトで、このローダーにより `next dev` の全ページが無限にリロードし続ける不具合が起きた。PostCSS 経由は Next.js 公式ドキュメントの方法。

### 1-5. pnpm のビルドスクリプト許可を明示する

- **決定:** `pnpm-workspace.yaml` の `allowBuilds` に、ビルドスクリプトを持つ依存(`@parcel/watcher` など)をすべて明示する。
- **理由:** pnpm 12 は記載のないパッケージがビルドスクリプトを持つと `pnpm install` を失敗させる。提出物を新しい環境にクローンして `pnpm install` した確認で発覚した。

### 1-6. 開発用の設定

- **決定:** ESLint(Next.js 標準)+ Prettier、`devIndicators: false`、`packageManager` で pnpm のバージョンを固定。
- **理由:** 評価者がそのまま実行できる標準構成にする。開発用の Next.js バッジは一覧の左下に重なるため表示しない。

## 2. UI・操作

### 2-1. 金額・割合の表記と損益の色

- **決定:**
  - 金額は半角の円記号で表示する(`¥115,500`。`ja-JP` は全角の `￥` になるため `en-US` で書式化)
  - 割合は小数第1〜2位(`5.0%`、`12.87%`)
  - 損益は `+15.5% (+¥15,500)` の形で、プラスは緑・マイナスは赤・ゼロはグレー。色に加えて符号を必ず付ける
- **理由:** ワイヤーフレームの表記に合わせる。色だけに頼らない(色覚の多様性への配慮)。

### 2-2. チャートの配色

- **決定:** 損益の緑・赤と混同しない、隣り合う色が似ない8色のパレット(CSS 変数)。一覧の各行の左端にも同じ色を表示する。
- **理由:** 当初は青が2色(VOO と PLTR)含まれていて区別しにくかったため変更した。

### 2-3. フォーカスの仕様

- **決定:** UI 要件の「フォーカスされた要素以外をクリックされたらフォーカスを外す」を次のように解釈し、操作を追加した。

  | 操作                                         | 結果                       |
  | -------------------------------------------- | -------------------------- |
  | チャートの要素をクリック                     | その銘柄をフォーカス       |
  | フォーカス中の要素を再度クリック             | 解除                       |
  | 別の要素をクリック                           | フォーカスを移す           |
  | 要素以外(背景・余白・チャート中央)をクリック | 解除                       |
  | 一覧の行をクリック(追加)                     | チャートと同じく切り替える |
  | Esc キー(追加)                               | 解除                       |
  | ↑ / ↓ キー(追加)                             | 前 / 次の銘柄に移す        |

- **理由:** 別の要素をクリックしたときは、解除してから選び直す手間がないよう、そのまま移す方が自然。
- **実装:** フォーカスの管理はカスタムフック `useHoldingFocus` にまとめた(当初は `PortfolioView` 内にあったが、画面の組み立てとロジックを分けるため切り出した)。

### 2-4. ↑↓キーでの移動

- **決定:** フォーカス中だけ↑↓キーで前後の銘柄に移す。先頭・末尾では止まり、反対側に回り込まない。修飾キー付きは扱わない。キーボードのフォーカスがチャートの要素・一覧の行にあれば同じ種類の次の要素へ移し、画面外の行は見える位置までスクロールする。
- **理由:** フォーカスがないときは矢印キーを通常どおりページのスクロールに使えるようにする。一覧の操作として、端で止まる方が予測しやすい。スクリーンリーダーで新しい銘柄が読み上げられる。
- **代替案:** ←→キーでチャートを回る操作は、今回は見送った。

### 2-5. チャート中央の表示

- **決定:** フォーカス中はその銘柄の名前・保有金額・損益を表示する(要件外の追加)。表示する4つの値は、フォーカス中の銘柄か全体かを一度だけ判定してまとめて決める。
- **理由:** 値ごとに `銘柄の値 || 全体の値` で切り替えると、損益が 0 の銘柄で 0 が「値なし」とみなされ、銘柄名と全体の損益が混ざって表示される不具合があった(レビューで発見し、修正前に失敗するテストを追加してから修正)。

### 2-6. ホバー表現と当たり判定

- **決定:** マウスを乗せた要素を少し拡大・明るくし、半透過中の要素は少し濃くする。ホバー表現は `@media (hover: hover)` の環境だけで有効。各要素は「見た目の図形」と「クリック・ホバーを受ける透明な図形」を重ね、拡大するのは見た目だけにする。
- **理由:** クリックできることを伝える。見た目の図形で判定すると、内側の縁で「拡大 → カーソルが外れる → 縮小」を繰り返してちらつく(E2E テストで発覚)。タップ後に強調が残らないようにする。
- **補足:** Tailwind v4 の `scale-*` は CSS の `scale` プロパティを使うため、トランジション対象も `scale` にする(`transform` を指定していたため、フォーカス時の拡大がアニメーションしていなかった)。

### 2-7. 連続クリック時のテキスト選択の防止

- **決定:** チャート全体で、2回目以降のクリック(`event.detail > 1`)だけ `mousedown` の既定動作を止める。
- **理由:** すばやく続けてクリックすると、ブラウザの「ダブルクリックで単語選択・トリプルクリックで行選択」が働き、テキストを持たないチャートの代わりに近くのテキストが選択されていた。
- **代替案:** 中央のテキストに `user-select: none` を付けるだけでは、選択が次に近いテキスト(一覧の見出し)へ移るだけで防げなかった(E2E テストで確認)。

### 2-8. 中央のテキストは選択不可にし、金額のコピーボタンを置く

- **決定:** チャート中央のテキストは選択できないようにし、代わりに金額の右にコピーボタンを置く。表示どおりの形式(`¥115,500`)でコピーし、チェックマークで完了を示す。コピーしてもフォーカスは解除しない(`data-preserve-focus`)。
- **理由:** 中央の表示はチャートの一部として操作される領域のため。金額をコピーしたい場合の手段は残す。
- **補足:** 中央表示の読み上げ(`aria-live`)は、コピー結果の読み上げと重ならないよう、画面に表示しない別の要素にまとめた。完了時の色は、文字色のクラスを1つだけにして指定する(複数付けると CSS の出力順で決まり、緑にならなかった)。
- **代替案:** 数値だけ(`115500`)をコピーする案もある。表計算ソフトは日本語設定で `¥115,500` も数値として扱えるため、表示どおりの形式を選んだ。

### 2-9. 読み込み中の表示

- **決定:** 読み込みが 200ms 以内に終わればスケルトンを出さない。出した場合は最低 500ms 表示する。切り替え時はフェードインする(`useDelayedLoading`)。
- **理由:** モック API はすぐに応答するため、スケルトンが一瞬だけ出てちらついていた。

### 2-10. レスポンシブ対応と最小幅

- **決定:** 最小幅は 320px(`body` の `min-width`)。一覧の各行は、上段(銘柄名|保有金額)と下段(ティッカー・保有割合|評価損益)を独立した行にする。
- **理由:** 320px は現在のスマートフォンの最小幅で、WCAG のリフロー基準。銘柄名が長い評価損益と幅を分け合わなくなり、360px 以上ではすべての銘柄名が省略されずに表示される(改善前は 412px 未満で一番長い銘柄名が省略されていた)。
- **代替案:**
  - CSS グリッドの2列構成は、列幅が上下の行で共有され、右の列が評価損益の幅になるため効果がなかった(計測で確認)。
  - 320px 未満のウィンドウでページ全体を縮小する案・「画面を広げてください」と表示する案は、文字が読めなくなる・内容が隠れるため見送り、横スクロールで表示する。なお、ブラウザのウィンドウ幅そのものをページ側から制限することはできない。

## 3. コードの書き方

### 3-1. メモ化の方針

- **決定:** すべてをメモ化せず、目的がある箇所だけにする。
  - `holdings` の並び替え(`useMemo`): `useHoldingFocus` のエフェクトの依存配列に入るため、参照を安定させる必要がある
  - フォーカス中の銘柄の検索(`find`): メモ化しない。7件の検索は軽く、`find` は配列内の同じオブジェクトを返すため参照もすでに安定している
  - `toggleFocus`(`useCallback`): フックの戻り値として参照を安定させておく
- **理由:** メモ化には前回の値の保持・依存配列の比較・可読性の低下という費用がある。重い計算、エフェクトの依存、`React.memo` の子への受け渡しのいずれかに当たるときだけ使う。
- **代替案:** React Compiler(自動メモ化)は、1画面のアプリではビルド構成をシンプルに保つことを優先して導入していない。

## 4. テスト

- **決定:**
  - 単体・コンポーネントテスト: Jest + React Testing Library
  - E2E テスト: Playwright。本番ビルドに対し、PC とスマートフォンの2つの画面サイズで実行する。再試行(retries)はしない
  - 不具合を直すときは、修正前に失敗するテストを先に書いてから直す
- **理由:** E2E は提出物に近い本番ビルドで確認する。再試行すると不安定なテストが隠れるため使わない。テストで実際に見つかった不具合: ホバーのちらつき、連続クリックでのテキスト選択、`user-select` だけでは防げない選択、狭い画面での銘柄名の省略、損益ゼロの表示。
- **E2E の注意点:** Playwright の `hover()`・`click()` は要素の外接矩形の中心を狙うが、円弧状の要素ではその点がドーナツの穴に落ちる。テストでは実際に塗られている点(`isPointInFill`)を探して操作する。
